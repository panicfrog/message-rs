# Data Hub Design (数据管理层)

Status: design agreed, M1 (Rust core) implemented; M2's spike passed on 2026-11-25 (cxx 1.0.205,
Xcode 26.1.1, Swift 6.2.1) and its corrections are folded into section 6. Decisions below were
settled in discussion on 2026-11-24; change them here first, then in code.

## 1. Role

An in-process pub/sub data layer on top of message-rs encoding. One Rust core (the "总控") owns
the subscription registry and the fan-out / last-value logic; every end embeds the same core via
FFI instead of reimplementing dispatch. Swift, Kotlin and RN are supported at the same time,
also inside one app: every surface links the same `message-hub` and talks to one process-wide
`Hub::shared()`. The core is a plain `lib` crate and must exist once per process — in a React
Native app it is compiled into the jsi-turbo aggregate library (`librust-app.a` / the `.so`),
never shipped as a second cdylib next to it.

| End | Surface | Wrapper |
|---|---|---|
| RN / JS | `hub-turbo`: a `#[RustTurboModule]` crate on jsi-turbo, built into the app's superlib | event-emitter ("mbox"-style) API over the generated TS bindings; `decodeBy(key)` |
| Kotlin | `hub-jni`: JNI methods with the `jni` crate, linked into the same `.so` (or a standalone one) | `external fun` declarations + SharedFlow/StateFlow-style wrapper, `Schema.kt` |
| Swift | `hub-ffi`: a `cxx` bridge (`extern "Rust"`), header generated by `cxx-build` | SwiftPM package: a Clang target exposing the header + a Swift target with C++ interop wrapping it; the public product is pure Swift, `Schema.swift` |

- **iOS is Swift Package Manager first.** React Native 0.89 (2026-12-05) makes SwiftPM the
  default with CocoaPods as an opt-out, and jsi-rs moves to SwiftPM-first with it; this
  project targets SwiftPM as the primary iOS integration and keeps podspecs only as a
  best-effort fallback while React Native still offers the opt-out. Two SwiftPM rules shape the
  Swift side: a target cannot mix Swift with C++ or Objective-C++, and there are no pod-style
  script phases.
- The Swift surface is a `cxx` bridge, the toolchain jsi-rs already uses (`jsi-sys`, `jsi`,
  `jsi-rn` all depend on `cxx`): the header is generated by `cxx-build` and imported by a Swift
  target with C++ interop, so it cannot drift from the Rust side, and the superlib gains no
  dependency. SwiftPM writes the module map for the Clang target itself; nothing is hand-written.
  The two targets stay separate because SwiftPM forbids mixing languages, and callbacks are
  function pointers that Swift registers at `subscribe` time, so there is no C++→Swift link
  dependency and no `-Swift.h` across targets — the trap mixed-language RN libraries hit under
  SwiftPM. A one-day spike gates the choice (M2 step 0); the fallback is a hand-written C header
  with the same bridge shape.
- RN push: `TurboCallback` serializes its arguments (`Vec<u8>` would become a JS number array),
  so the callback is only a wake-up carrying the id; JS pulls the bytes as a zero-copy
  `JsiArrayBuffer`, which the hub's pull (newest value per publisher) already provides.

The core is payload-agnostic: it moves `(id, kind, bytes)` and knows no schema, mirroring the
schema-free runtimes of the three languages.

## 2. Data model

A data item is `(id: u32, kind: ValueKind, payload: bytes)`, owned by a publisher.

- `ValueKind` (stable u8 discriminants, they cross FFI):
  `Bool=0, U8, I8, U16, I16, U32, I32, U64, I64, F32, F64, String=11, Bytes=12, Message=13`
  — order matches `message_core::SimpleType`, plus `Message`.
- Byte layouts follow message-rs wire conventions: little-endian scalars, `bool` one byte,
  `String` raw UTF-8 (payload length is the length), `Bytes` raw.
- `Message` payloads are message-rs encodings; the item id is then the message key, so ends can
  decode by key with their generated code. Core does not enforce the id/key match.
- Basic kinds exist so simple values (flags, counters, strings) do not need a struct per value.
- A **publisher** is an explicit RAII handle bound to one `(id, kind)`; the kind is fixed for its
  lifetime (a publisher is a source of exactly one type, so ends can expose `Publisher<T>`).
  Several publishers may share an id. All publishing goes through a handle — there is no one-shot
  `hub.publish(id, ...)`, because an ephemeral publisher would make "the last publisher closed"
  meaningless.

## 3. Semantics (settled)

- **Push**: `subscribe(id, cb)` is pure forwarding. Subscribing never replays the last value.
- **Pull**: the hub stores nothing. Each publisher keeps the payload of its own last publish;
  `get(id)` returns the newest of those among the id's *live* publishers, `None` when none ever
  published or none is left. Pull runs no user code. (A lazy provider — `get` calling into the
  publisher for a value newer than its last push — was considered and deferred: it would put
  user code inside `get`, with the same re-entrancy, threading and FFI ctx-lifetime issues as
  dispatch. It can be added later without changing anything else here.)
- **Lifecycle**: closing the last live publisher of an id delivers `Event::Closed` to its
  subscribers — exactly once, after every value in synchronous mode — and `get` returns `None`
  from then on. Subscriptions survive `Closed`: a new publisher on the same id reaches them again.
  Publishing after `close` is a silent no-op; `close` is idempotent (`Drop` closes as well).
- **No subscribers**: `publish` silently records the value and returns (pull still works).
- **Delivery order**: a single internal lock serializes the registry update of every publish, so
  publishes from one thread arrive per id in order and the newest value always wins in `get`;
  callbacks run outside the lock on a snapshot of the subscriber list, so across publisher
  threads every delivery happens but their relative order is unspecified:
  - unsubscribing inside a callback: the callback already running completes, the next delivery
    misses; a subscriber unsubscribed earlier in the same dispatch is skipped;
  - subscribing inside a callback: does not receive the current delivery;
  - publishing or closing inside a callback is allowed and dispatches recursively (re-entrancy
    is the caller's responsibility; no cycle protection).
- **Failures**: callbacks cannot fail (fire-and-forget). Inline subscribers run on the
  publisher's thread, so a slow callback blocks its publisher — the escape hatch is
  `subscribe_on` (below).

## 4. Threading model

- `Hub: Send + Sync` over an `Arc<Inner>` (so `Hub` is cheap to clone and shares one registry);
  `Inner` holds `Mutex<State>`. The lock guards the registry — which ids exist, their
  subscribers, their live publishers and each one's last value — and never user code: dispatch
  and `Closed` notifications run outside it.
- `State { ids: HashMap<DataId, Entry>, seq }`,
  `Entry { subs: Vec<Arc<SubState>>, pubs: Vec<PubRec> }`, `SubState { cb, alive, scheduler }`,
  `PubRec { kind, seq, last }`. `seq` is a global counter stamped at each publish; `get` picks
  the live record with the greatest `seq` that has published. An entry is removed once it has
  neither subscribers nor live publishers.
- **Why the lock stays**: explicit handles solve lifetime (`Arc` + RAII), not mutual exclusion —
  handles are created and dropped from any thread and every publish still needs a snapshot of
  the subscribers. Critical sections are a map lookup plus one `Arc` clone per subscriber;
  per-id locks are a later option only if contention is ever measured.
- **Snapshot**: everything handed to user code outside the lock is an immutable owned value —
  the payload (`Arc<[u8]>`, replaced per publish, so a running callback never sees a torn or
  newer buffer) and the subscriber list (cloned per publish). A delivery skips subscribers whose
  `alive` flag is clear; that makes unsubscribe take effect as early as possible and, under FFI,
  lets a trampoline ctx be freed with its last `Arc` instead of at unsubscribe time.
- **Scheduler per subscription**: `Scheduler = Arc<dyn Fn(Box<dyn FnOnce() + Send>) + Send + Sync>`.
  `subscribe` runs callbacks inline on the publisher's thread; `subscribe_on` hands each
  delivery of that subscriber to its scheduler, which lands it on its own loop (Swift main
  queue / dispatch queue, Kotlin handler or coroutine dispatcher, RN JS thread via the
  CallInvoker). It is per subscriber rather than per hub because one shared hub serves several
  loops at once and a hub-wide setting would be last-writer-wins. For scheduled subscribers
  `publish` returns before callbacks run; ordering becomes the scheduler's property, and `get`
  inside a callback may already return a value newer than the one being delivered — callbacks
  must use their arguments.
- **Shared instance**: `Hub::shared()` is one registry per process; the three surfaces all use
  it, so a JS subscriber sees a Kotlin publisher. `Hub::new()` stays for isolated registries
  (tests, tools).
- **Subscription**: RAII (`Drop` unsubscribes) plus an idempotent explicit `unsubscribe()`.
- **Publisher**: RAII (`Drop` closes) plus an explicit idempotent `close()`. Both handles hold a
  `Weak` reference to the hub, so using or dropping them after the hub is harmless. Ends with
  nondeterministic destruction (Kotlin) must expose `close()` and call it from their lifecycle
  (`ViewModel.onCleared`), otherwise pull outlives the object.

## 5. Core API (crate `message-hub`, dir `hub/`, zero dependencies)

```rust
pub type DataId = u32;

/// What a subscriber receives: a published value, or the end of every publisher of its id.
pub enum Event<'a> { Value(ValueKind, &'a [u8]), Closed }

pub type Callback = Arc<dyn Fn(DataId, Event<'_>) + Send + Sync>;

impl Hub {
    pub fn new() -> Self;
    pub fn shared() -> &'static Hub;                                    // one per process
    pub fn publisher(&self, id: DataId, kind: ValueKind) -> Publisher;
    pub fn subscribe(&self, id: DataId, cb: Callback) -> Subscription;            // inline
    pub fn subscribe_on(&self, id: DataId, cb: Callback, s: Scheduler) -> Subscription;
    pub fn get(&self, id: DataId) -> Option<(ValueKind, Arc<[u8]>)>;   // pull
    pub fn get_value(&self, id: DataId) -> Option<Result<Value, ValueError>>;
}

impl Publisher {                       // RAII: Drop closes
    pub fn id(&self) -> DataId;
    pub fn kind(&self) -> ValueKind;
    pub fn publish(&self, payload: &[u8]);
    pub fn publish_value(&self, v: &Value) -> Result<(), ValueError>;  // Err on kind mismatch
    pub fn close(&self);               // idempotent
}

impl Subscription {
    pub fn id(&self) -> DataId;
    pub fn unsubscribe(&self);         // idempotent
}
```

`hub/src/value.rs` — the value codec module:

- `ValueKind`: `Copy`, `#[repr(u8)]`, stable discriminants per section 2, plus `from_u8(u8)`
  and `fixed_len() -> Option<usize>` (fixed-size kinds only);
- `Value`: one variant per kind (`Bool(bool)` … `F64(f64)`, `String(String)`, `Bytes(Vec<u8>)`,
  `Message(Vec<u8>)`), with `kind()` and `encode() -> Vec<u8>` (little-endian scalars, raw
  UTF-8 / raw bytes, `Message` passthrough);
- `decode(kind, &[u8]) -> Result<Value, ValueError>`: fixed-size kinds reject wrong lengths,
  `String` rejects invalid UTF-8, `Bytes` / `Message` pass through; `ValueError(&'static str)`.

## 6. Milestones

- **M1 (done)** — Rust core: `hub/Cargo.toml` (crate `message-hub`, zero dependencies),
  `hub/src/value.rs`, `hub/src/lib.rs` (`Hub`, `Publisher`, `Subscription`, `Event`,
  `Scheduler`), `hub/tests/hub.rs` (section 7); `hub` is a root workspace member.
- **M2** — `hub-ffi` (dir `hub/ffi/`) plus the SwiftPM package `MessageHub` (dir `hub/apple/`):
  the Swift surface as a `cxx` bridge, on the toolchain jsi-rs already uses (`cxx` /
  `cxx-build` are in every jsi-turbo superlib, so this adds no dependency there; UniFFI stays
  ruled out). Plan, in order:
  0. **Spike — done, passed** (2026-11-25; throwaway, not in this tree). Every step held with
     one correction and three findings that shape step 1:
     - **cxx does not accept function pointers from C++ to Rust** ("not implemented yet"), so
       the callback crosses as an opaque address (`*const u8`, transmuted back on the Rust
       side) — the same representation on every ABI we target. There is no `extern "C"` block
       in a bridge either; C fn types are written inline as `unsafe extern "C" fn(...)`.
     - **Swift cannot construct `rust::Slice`** (its raw-pointer constructor is not imported), so
       `&[u8]` arguments cross as `(ptr: *const u8, len: usize)`; `Vec<u8>` returns are fine
       (Swift imports `size()` and the subscript, not `data()`/`begin()`).
     - Opaque Rust types are imported as a bare `OpaquePointer` (the `namespace.Type` spelling
       does not exist in Swift); functions taking raw pointers must be `unsafe fn` in cxx
       1.0.205; `extern "Rust"` items are implemented in the bridge module's parent.
     - The test target needs `interoperabilityMode(.Cxx)` too (SwiftPM rebuilds the Clang module
       for it, otherwise as Objective-C), and `cxxLanguageStandard: .cxx17` is a `Package(...)`
       argument. SwiftPM caches a `binaryTarget` by path: the build script must remove the old
       xcframework before writing the new one.
  1. **The bridge** (`hub/ffi/src/bridge.rs`, `#[cxx::bridge(namespace = "message_hub")]`):
     opaque `Hub`, `Publisher`, `Subscription`; handles are raw pointers (`*mut T`), so Swift
     never meets a move-only `unique_ptr` — RAII lives in the Swift wrapper's `deinit`.
     `shared() -> &'static Hub`, `create()` for isolated tests, `release`; `publisher(h, id,
     kind_u8)`, `publish(p, ptr: *const u8, len: usize)`, `close(p)` / `release(p)`;
     `subscribe(h, id, cb: *const u8, ctx: *mut u8)` and `subscribe_on(h, id, cb, ctx, schedule:
     *const u8, schedule_ctx: *mut u8)`. The Swift side passes a `@convention(c)` closure cast to
     a pointer (the trampoline) plus a retained context box, and exports the trampoline as a
     file-private static so it is never a capturing closure. A reserved `kind_u8` (255) delivers
     `Closed` as `ptr = null, len = 0`. `unsubscribe(s)` / `release(s)`; `get(h, id) -> Vec<u8>`,
     empty meaning `None`. Every function is infallible — no `Result`, so no C++ exception ever
     crosses a Swift frame.
  2. **Build and packaging**: `hub/ffi/build.rs` runs `cxx-build` (`cargo test` compiles the
     glue and covers the bridge). The generated header and the `cxx` runtime headers are
     exported into `hub/apple/Sources/MessageHubCxx/include/` and committed, like every other
     generated artifact here, with a CI freshness check. The package has four targets:
     `MessageHubCxx` (Clang, headers only — SwiftPM writes its module map), `MessageHubRust`
     (`binaryTarget`: an xcframework holding `libhub_ffi.a` with the core inside, device,
     simulator and macOS slices, built by `hub/apple/scripts/build-xcframework.sh`, gitignored),
     `MessageHub` (Swift with C++ interop, depending on both) and `MessageHubTests` (also with
     C++ interop). C++ interop is switched on only for the two Swift targets; the product apps
     see is pure Swift.
  3. **Acceptance**: a C++ round-trip test (`hub/ffi/tests/roundtrip.cpp`, compiled by the test
     build against the bridge) covering publish / subscribe / `get` / `Closed` / close; the
     package's Swift tests decode a message vector published from Rust via `Schema.swift`.
- **M3** — the Swift wrapper inside the same package: `Hub`, `Publisher<T>` and `Subscription`
  as RAII types over the raw handles, an `AsyncSequence` of events and an `ObservableObject`
  mirror per id, `subscribe_on` mapped onto a `DispatchQueue` or `@MainActor`. Conformance:
  message vectors published from Rust, decoded in Swift via `Schema.swift`.
- **M4** — `hub-jni` (dir `hub/jni/`, `jni` crate) + Kotlin wrapper over `external fun`; same
  conformance via `Schema.kt`. The wrapper owns the publisher handles and must close them from
  its lifecycle (`ViewModel.onCleared`), not rely on GC. Android is unaffected by the SwiftPM
  move: the cargo build keeps running from the gradle `rustTurboBuild` task.
- **M5 (local verification done; in-app conformance pending)** — `hub-turbo`: a jsi-turbo module package (an npm package whose crate is built into the
  app's superlib, the way `example/native/jsi-demo-module` is in jsi-rs); JS emitter API +
  `decodeBy` integration; push as wake-up + zero-copy pull. Metadata is SwiftPM-first
  (`Package.swift` + `swiftpmConfig` in `package.json`), with a podspec only for apps that opt
  out of SwiftPM. It depends on jsi-rs gaining its own SwiftPM path (the cargo hook moving off
  the pod script phase) and settles one open point with it: in a React Native app the hub
  symbols come from the superlib, so the Swift wrapper needs a link mode without its own
  xcframework.
- **M6 (later)** — metrics, cross-process transport (only if needed). Retention is no longer a
  topic: nothing is stored once the publishers are gone.

CI covers every surface: `cargo test --workspace` (core + the JNI Java twin), `hub-swift`
(builds the xcframework, then swift test), `hub-kotlin` (cargo builds the host dylib, then
gradlew test with -PhubLibDir), `hub-turbo` (tsc + vitest on the emitter layer). The RN app
build itself stays out of CI — it needs pods/NDK and a running app.

All three surfaces are value-first: Swift `publish(id:, UInt16(65535))` / `pull(id:)`, Kotlin
`publish(1, 65535.toUShort())` / `pull(1)`, JS `publish(id, u16(65535))` / `pull(id)`. Swift and
Kotlin need no wrappers at all — their type systems distinguish `UInt16` from `Int32` from
`Double`, so the kind follows the type exactly (`HubValue` / `hubValueOf`); `MessageBytes` marks
a message-rs payload on both. Handles are managed per (id, kind) internally on every end.

The wire kind is an implementation detail, not part of the API. JS callers write
`publish(id, 65535)` or `publish(id, u16(65535))`, `pull(id)`, `close(id)` — no handles and no
`ValueKind` at the call site. Plain values map by a fixed rule (boolean→BOOL, string→STRING,
bigint→I64, Uint8Array→BYTES, number→F64); the wrappers (`u8`…`f64`, `message`) pin an exact
width. Value-range guessing was rejected: it would change the wire format as values change and
break cross-language decoding. Publisher handles are managed per (id, kind) internally.

`pull<T>(id)` / `channel<T>(id, h)` take a **compile-time hint only**: `as T` erases at runtime,
so the value is always the decoding of the sender's real kind. Declaring `pull<string>` on an id
holding a u16 still yields the number — the hint saves a narrowing step, it never converts or
validates. Two tests pin this.

Decoding is the surface's job, not the caller's: the kind is known, so basic types arrive as
values on every end — Swift/Kotlin `Value.decode`, JS `pull()` returning boolean/number/bigint/
string and `channel()` events carrying `value`. Only `MESSAGE` stays binary (it needs the
generated schema); `pullRaw()` remains for byte-level work. The JS side used to hand back raw
bytes plus a separate `lastKind()`, which pushed a DataView onto every call site — fixed.

One Rust copy per process (the demo's prerequisite, see example/PLAN.md): each surface used to
ship its own core, and symbol inspection showed three distinct `Hub::shared::SHARED` statics
with different crate hashes — the linker never coalesces them, so the ends could not see each
other. Fixed by making `hub-turbo` carry the platform's native surface (iOS/macOS: `hub-ffi`,
Android: `hub-jni`), so installing that one package links a single core. The Swift package gains
a superlib mode (`MESSAGE_HUB_SUPERLIB=1`: headers only, no xcframework) and the Kotlin wrapper
a library-name switch (`-Dhub.libName=rust_app`). Verified: an aggregate of core + hub-ffi has
exactly one SHARED static and both symbol sets; both Swift modes build; all existing tests pass.

Distribution (to confirm): `message-hub` and the two RN-independent surfaces (`hub-ffi`,
`hub-jni`) as crates.io crates — pure Rust, no React Native version coupling — so the superlib's
cargo build resolves them normally; `hub-turbo` ships as an npm package the jsi-turbo way; the
Swift package stays in `hub/apple/` and is consumed as a local package first, its own
distribution can wait.

## 6b. Unified encoding protocol (基本类型与生成的结构体一视同仁)

Settled in discussion on 2026-11-27. The value-first API above only knew basic types; a
message-rs struct had to be hand-encoded (`User.encode(u)`) and wrapped (`MessageBytes(bytes)`)
to publish, then hand-decoded on pull — two encodings exposed to the caller, and "what can be
published" was a hardcoded list. Fixed by one protocol per end that both basic types and
generated structs conform to; extending it later is implementing the protocol, not touching the
hub.

**Architecture: hub and runtime stay independent, integrated by composition.** The runtime
(each end's `MessageRuntime` / `message.rs` / `runtime.ts`) defines the codec protocol; generated
code already conforms to it using its existing `encode()`/`fromBytes`. The hub still only moves
`(kind, bytes)` and knows no schema — it depends on the runtime package for the protocol type
only (pure Swift/Kotlin/TS, no Rust symbols), never the other way around. No circular dependency:
generated code already imports its runtime.

| End | Runtime protocol | Hub integration |
|---|---|---|
| Swift | `MessageCodec` (`messageKey`, `encode() -> Data`, `static fromBytes(Data) -> Self?`) in `MessageRuntime` | `Hub.publish<T: MessageCodec>` / `pull<T: MessageCodec>` overloads alongside the `HubValue` ones — Swift cannot declare a blanket conformance to a local protocol for a type from another module, so two overloads share one private implementation instead |
| Kotlin | `MessageEncodable` (instance: `encode()`) + `MessageCodecCompanion<T>` (companion: `messageKey`, `fromBytes`) in `message.rs` — split because Kotlin keeps `fromBytes` on the companion, same pattern as the existing `MessageEnumCompanion` | `hubValueOf` checks `is MessageEncodable` once (covers every generated type); `hub.pull(id, User.Companion)` — the companion is passed explicitly, no registry |
| TS | `MessageCodec<T>` (`key`, `encode(value)`, `fromBytes(buf)`) in `runtime.ts`; each namespace exports `codec: MessageCodec<T>` | `publish(id, value, codec)` / `pull(id, codec)` / `channel(id, codec, handler)` overloads. A plain JS object has no reliable runtime brand to guess its schema from (unlike Swift/Kotlin's nominal types), so the codec is named once at the call site instead of guessed per value or looked up in a registry |

No auto-registration registry on any end (considered for TS/Kotlin, rejected): Swift/Kotlin don't
need one (nominal types / an explicit companion argument already carry the identity), and giving
TS one too would mean a third mechanism for the same job. `MessageBytes` stays on Swift/Kotlin as
the escape hatch for a payload without a schema on hand.

Two build-layout findings while wiring the runtime dependency in:
- **`hub/swift` renamed to `hub/apple`.** SwiftPM derives a local package's identity from its
  directory's basename when the manifest is pre-6.0; both `hub/swift` and `runtime/swift` ended
  in `swift`, which SwiftPM read as a package depending on itself ("cyclic dependency" at
  tools-version 5.9, or a product-not-found misresolution at 6.0+) regardless of the declared
  `name:` override. Renaming the directory sidesteps the collision with no tools-version bump;
  `hub/kotlin`/`hub/turbo` never had this problem (different basenames already).
- Kotlin wires the runtime in through a Gradle composite build (`includeBuild("../../runtime/kotlin")`
  in `hub/kotlin/settings.gradle.kts`, substituted by the `message.rs` group added to the
  runtime's subprojects) — the source-dependency equivalent of Swift's local `.package(path:)`,
  no published artifact needed. TS uses a `file:../../runtime/ts` devDependency.

## 7. M1 test list

1. subscribe → publish → callback receives `(id, kind, bytes)`;
2. publish with no subscribers is silent, `get` still returns the publisher's last value;
3. multiple subscribers all receive, in registration order;
4. dropping `Subscription` stops deliveries;
5. explicit `unsubscribe()` is idempotent;
6. `get` returns the latest after several publishes;
7. subscribing does not replay the last value;
8. unsubscribing inside a callback: the callback completes, the next delivery misses; a
   subscriber unsubscribed earlier in the same dispatch is skipped;
9. publishing another id inside a callback works;
10. `get` inside a callback returns the value being delivered (through a cloned `Hub`);
11. concurrent publish/subscribe/unsubscribe/close across threads: no deadlock, everything
    delivered to the subscribers that stayed;
12. `subscribe_on`: a subscriber's deliveries (values and `Closed`) run on its own executor, not
    the publisher thread, while `get` is updated synchronously; two subscribers on different
    executors each land on their own and an inline subscriber stays on the publisher thread;
13. `Value` encode/decode round-trips for every kind; wrong lengths and invalid UTF-8 rejected;
14. using and dropping handles after the hub does not panic;
15. the kind is fixed per publisher: `publish_value` rejects a mismatched kind, and `get` reports
    the kind of the publisher that answered;
16. `get` is `None` before any publish and once the last publisher is closed; a second live
    publisher keeps pull working and `get` answers with the newest publish;
17. closing the last publisher delivers `Closed` to every subscriber exactly once, after every
    value; closing a non-last publisher delivers nothing;
18. publishing after `close` is a silent no-op; `close` is idempotent across explicit calls and
    `Drop`;
19. closing inside a callback is allowed and dispatches the other id's `Closed` recursively;
20. subscriptions survive `Closed` and receive values again from a new publisher;
21. `Hub::shared()` is one registry per process: a value published through one clone is
    received by a subscriber registered through another.

- M4 is complete. `hub/jni/` (crate `hub-jni`) exposes every entry point under **two** symbol

  the JVM resolves the short name (an `internal` modifier also mangles the name: external
