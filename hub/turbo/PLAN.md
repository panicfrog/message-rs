# M5: hub-turbo (RN / JS surface) — implementation plan

Status: steps 1, 2, 4 and 5 are done (2026-11-26); only step 3 (in-app conformance on a
running RN app) remains. Findings recorded below.

## Shape

An npm package whose Rust crate is built into the app's aggregate superlib (the
react-native-rust-turbo way), exactly like `jsi-demo-module`:

```
hub/turbo/
  Cargo.toml      crate "hub-turbo", crate-type ["lib"], standalone workspace
  package.json    main: generated/rust-turbo/Hub.ts, rust-turbo metadata { crate, crateName, modules: ["Hub"] }
  src/lib.rs      #[RustTurboModule("Hub")] over message-hub
  generated/rust-turbo/Hub.ts   (generated by the framework, committed like other artifacts)
```

## Rust module (src/lib.rs)

Modelled on the demo's `Ticker` (an event source with JS callbacks) plus pull methods:

- `subscribe(id: f64, cb: TurboCallback) -> f64` — returns a subscription id (JS holds it,
  calls unsubscribe with it). The TurboCallback hops to the JS thread via the CallInvoker,
  which solves the threading contract for free (no manual scheduler).
- `unsubscribe(sub_id: f64) -> f64` (idempotent).
- `publish(id: f64, kind: f64, data: JsiArrayBuffer) -> f64` — the JS side hands the bytes
  as an ArrayBuffer; Rust reads them in place.
- `get(id: f64, rt: &mut RuntimeHandle) -> JsiArrayBuffer` + a kind out-param — the pull
  path returns the newest payload zero-copy (`JsiArrayBuffer::from_vec` over the hub's
  stored bytes; the empty-buffer case means "nothing published"). Kind travels in a small
  struct (`Pulled { kind, bytes }` via TurboStruct) so JS gets `{ kind, bytes }`.
- `close_publisher(pub_id)`, publisher handles returned by `create_publisher(id, kind)`.
- The module itself wraps `Hub::shared()`: one registry per process, the same instance the
  Swift and Kotlin surfaces see in a hybrid app.

State on the Rust side: `HashMap<u64, (Subscription, TurboCallback-registrations)>` behind
a Mutex, mirroring the JNI bridge's ctx model but with TurboCallback instead of GlobalRef.
Closed arrives as the callback invoked with `{ kind: 255, bytes: null }`-shaped event.

## JS surface

The generated `Hub.ts` gives `getHub()` with the method table above. On top of it (plain
TS, in the package):

- `HubChannel`-style emitter: `subscribe(id, handler)` returning an unsubscribe fn; events
  arrive as `{ kind, bytes: ArrayBuffer | null }`; `decodeBy(key)` from the generated
  message schema decodes `MESSAGE` payloads.
- Push is wake-up + pull: the callback fires, JS calls `get(id)` for the current bytes
  (zero-copy ArrayBuffer). This matches DESIGN section 1's RN row and keeps the JS side
  free of payload buffering.

## Verified so far

- `hub/turbo` installs into the jsi-rs example app by `file:` symlink; the superlib build
  (build.js, `aarch64-apple-darwin`) compiles `hub-turbo` in with the `Hub` force anchor and
  produces `librust_app.a`.
- The macros emit `generated/rust-turbo/Hub.ts` (+ `structs/`) during that build — committed
  like every other generated artifact.
- `message-hub` resolves by **absolute path** in hub-turbo's Cargo.toml: cargo follows path
  deps through the npm symlink's literal directory, not the link target. A published version
  replaces this with a crates.io dependency.
- The TS layer (`index.ts`: channel/pull/publish/publisher handles) typechecks standalone
  (`types.d.ts` declares the `require` the generated bootstrap uses) and has 5 vitest tests
  against a fake native module modelling the core's semantics: wake-up + pull, handle routing,
  Closed once with subscription revival, unknown-handle publish returning false, and the Rust
  message vector byte-for-byte.
- The superlib really registers the module: `nm librust_app.a` shows `___jsi_turbo_force_hub`
  defined in a hub_turbo object, exactly like the demo's ticker/turbo_demo anchors.
- API shapes that fell out of the macro's constraints: `get` returns the ArrayBuffer alone
  (JsiArrayBuffer is not serde-serializable, so it cannot sit in a TurboStruct); the kind
  rides a thread-local read by the `kind` getter right after. `publish` routes through a
  registered publisher handle — a one-shot publisher would close on drop and deliver Closed
  spuriously.

## What cannot be done on this machine now

- The crate depends on `jsi`/`jsi-turbo` by path into node_modules
  (`../react-native-rust-turbo/rust/...`), which only exists inside an RN app's
  node_modules. Compiling requires either the example app (React Native 0.88 + pods +
  Xcode build) or refactoring those paths.
- The generated TS bindings are produced by the framework's codegen during the app build.

## Steps

1. Scaffold `hub/turbo/` (Cargo.toml, package.json, src/lib.rs) following the demo module
   verbatim; the hub logic is small (subscribe/publish/get/close over the core).
2. Local compile check: copy the crate into the jsi-rs example app's native dir (or point
   the example app's package.json at our path) and let the superlib build compile it —
   this validates the Rust side without touching jsi-rs.
3. Conformance in the example app: a Jest/TS test (or App screen) driving publish/get/
   subscribe/Closed through the hub from JS, against the Rust vector hex for byte equality.
4. Copy the generated `Hub.ts` back into the package (committed), add the JS emitter layer
   and its unit tests (mock the generated accessor).
5. CI: the package's `tsc` + vitest on the TS layer (no RN build in CI); the Rust side
   rides on the workspace's cargo test via a `hub-turbo-core` pure-Rust unit split if the
   jsi deps can't compile outside an app. Decide when step 2 lands.

## Open points (decide while implementing)

- Whether publisher handles need to be JS-visible objects (TurboObject) or plain ids —
  ids first, matching the JNI surface.
- `JsiArrayBuffer::from_vec` for the pull path: the hub's payload is behind an `Arc<[u8]>`;
  from_vec takes ownership, so the pull copies once (Arc -> Vec). Acceptable; zero-copy
  would need a from_arc API in jsi-rs.
- The Swift superlib link-mode question stays deferred (see DESIGN.md M2 note).
